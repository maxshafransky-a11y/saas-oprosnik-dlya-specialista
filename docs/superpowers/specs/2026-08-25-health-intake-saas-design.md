# Secure Health Intake SaaS — архитектурная спецификация

- Дата: 2026-08-25
- Автор: Codex совместно с владельцем продукта
- Статус: готово к проверке владельцем продукта
- Размер решения: Bulletproof L, модульный монолит

## 1. Результат

Создаётся защищённый русскоязычный SaaS-модуль фиксированной анкеты здоровья. Владелец распространяет одну постоянную ссылку. Клиент сам указывает email, подтверждает его magic link либо шестизначным кодом, заполняет 46 вопросов с автосохранением, прикладывает анализы, проверяет и отправляет анкету. Позднее клиент может исправить ответы; предыдущая отправленная версия остаётся неизменной, а актуальной становится последняя отправка.

V1 готовится как самостоятельный модуль, который открывается верхнеуровневой ссылкой и позднее подключается к основной платформе без переписывания анкеты или хранения.

## 2. Приоритет источников

При конфликте применяется следующий порядок:

1. Последнее явно подтверждённое решение владельца продукта.
2. Эта спецификация.
3. `.superdesign/design-system.md` и утверждённые локальные макеты.
4. `2026-08-25-health-intake-questionnaire-source.md`, извлечённый через Google Drive из таблицы `опрос`, как канонический источник текстов, порядка, типов, вариантов и подсказок.
5. Явная политика requiredness и условности из этой спецификации: исходная Drive-таблица этих свойств не содержит.

Отсюда следуют три намеренных изменения старых макетов:

- «личная ссылка» означает постоянную публичную ссылку workspace, а не секретную ссылку клиента;
- письмо сначала предлагает magic link, код остаётся запасным способом;
- экран завершения остаётся визуально тем же, но получает действия `Исправить ответы` и `Добавить документы`.

## 3. Цели и критерии успеха

### Цели

- Минимизировать действия владельца: отправить одну ссылку вручную или будущим ботом.
- Не требовать от клиента регистрации и пароля.
- Не терять длинный ввод при закрытии страницы, сбое сети или повторном входе.
- Не допускать незаметного изменения уже отправленных медицинских данных.
- Безопасно принимать анализы и другие документы.
- Сохранить возможность будущего SaaS-разделения по workspace и интеграции с основной платформой.

### Измеримые критерии

- Новый клиент доходит от публичной ссылки до первой секции через согласие, email и одно действие в письме; код доступен без отдельного запроса.
- После успешного входа повторное открытие той же ссылки на том же устройстве возобновляет анкету, пока действует сессия.
- Каждый автосохранённый ответ восстанавливается с сервера после повторной авторизации.
- Ни одна незавершённая правка не изменяет последнюю отправленную версию.
- Файл нельзя скачать до статуса `ready` и без авторизации в том же workspace/client scope.
- Все 46 вопросов и 10 разделов проходят автоматическую структурную проверку и ручную сверку с канонической формой.

## 4. Scope V1

### Входит

- Постоянная публичная ссылка workspace.
- Отдельный экран согласия и ссылка на политику конфиденциальности.
- Ввод email, magic link и резервный шестизначный код в одном письме.
- Серверная сессия без пароля.
- Фиксированная анкета из 10 разделов и 46 вопросов.
- Условный вопрос по указанному полу.
- Серверное автосохранение, возобновление и обработка конфликта двух вкладок.
- Экран проверки перед отправкой.
- Неизменяемые версии отправок и явное повторное редактирование.
- Загрузка, проверка, просмотр статуса, скачивание и удаление собственных документов.
- Аудит чувствительных действий.
- Адаптивный интерфейс по утверждённой дизайн-системе.
- Подготовленная граница для будущего handoff/webhook, без реализации неизвестной внешней платформы.

### Не входит

- Редактор анкет и произвольные шаблоны.
- Кабинет или CRM специалиста.
- Роли команды, биллинг и подписки.
- ИИ-анализ, OCR, диагноз, лечебные рекомендации или экстренная помощь.
- Нативное мобильное приложение и offline-first.
- Telegram-авторизация или загрузка медицинских файлов в бота.
- Iframe как основной способ внедрения.
- Семейные профили под одним email.
- История каждого нажатия клавиши или event sourcing.

## 5. Пользователи и доверительные границы

### Клиент

Получает публичную ссылку, подтверждает свой email, работает только со своей карточкой, ответами и документами.

### Владелец/специалист

В V1 не имеет отдельного интерфейса этого модуля. Распространяет одну ссылку. Просмотр результата будет выполняться через будущую основную платформу или отдельный последующий scope.

### Внешние системы

- Email-провайдер получает адрес и техническое письмо, но не содержимое анкеты.
- S3-compatible storage хранит только закрытые бинарные объекты.
- ClamAV получает поток файла для локальной проверки.
- Будущая платформа получает данные только через отдельно согласованный и подписанный контракт.

Бот может отправлять публичную ссылку, но не принимает email, ответы, токены или файлы здоровья.

## 6. Клиентский путь

```text
Постоянная ссылка workspace
  → согласие
  → ввод email
  → письмо: magic link + код
  → подтверждённая серверная сессия
  → анкета с autosave
  → проверка
  → immutable submission v1
  → завершение
      ├─ добавить документы к карточке
      └─ исправить ответы → editing → immutable submission v2
```

### 6.1 Первичный вход

1. `GET /i/{public_slug}` показывает назначение анкеты, примерную длительность, конфиденциальность, обязательную непредвыбранную галочку согласия и ссылку на политику.
2. `POST /i/{public_slug}/consent` проверяет галочку и создаёт короткоживущий подписанный pre-auth cookie, привязанный к workspace, с версией/хешем текста, временем принятия и expiry.
3. Клиент вводит email. Ответ сервера всегда нейтрален и не раскрывает, существует ли карточка.
4. Система создаёт один `login_challenge` и отправляет одно письмо с кнопкой magic link и кодом.
5. Magic link открывает минимальную same-origin страницу, которая передаёт token из URL fragment в POST; корректный magic token либо код одноразово потребляет challenge.
6. В одной транзакции создаётся или находится client, фиксируется consent и создаётся session.
7. Клиент попадает на незавершённый раздел, экран проверки либо экран завершения в зависимости от состояния response.

### 6.2 Возврат

- При действующей cookie-сессии публичная ссылка сразу продолжает карточку после проверки workspace.
- При истёкшей сессии клиент повторяет email-подтверждение; сохранённые ответы остаются на сервере.
- Одна карточка V1 определяется уникальной парой `(workspace_id, email_normalized)`.

### 6.3 Исправление после отправки

1. Экран завершения показывает номер и время текущей отправки.
2. `Исправить ответы` переводит response из `submitted` в `editing`; текущие рабочие answers начинаются с данных последней отправки.
3. Незавершённые правки помечаются `Изменения не отправлены` и видны только клиенту.
4. Читающая сторона продолжает получать последний submission.
5. Новая отправка создаёт следующий immutable snapshot и становится актуальной.

## 7. UX/UI-контракт

Визуальный источник истины — `.superdesign/design-system.md`. Эталон широкого раздела — `.superdesign/tmp/nutrition-v6.html`; карта потока — `.superdesign/tmp/ux-flow-map.html`.

### Desktop

- Тихая левая панель прогресса шириной 280 px.
- Одна широкая центрированная колонка анкеты с `max-width: 960px`.
- Форма не переносится в узкую правую колонку.
- В разделе 2–7 просторных карточек вопросов и одна основная кнопка `Продолжить`.

### Mobile

- Один естественно прокручиваемый столбец от 320 px.
- 16 px боковых отступов.
- Sticky-прогресс сверху и нижняя панель действий, не закрывающая активное поле.
- Никаких фиксированных высот, обрезанных карточек или горизонтального скролла.

### Обязательные правила взаимодействия

- Single choice реализуется одной нативной radio-группой с общим `name`; одновременно выбран ровно один вариант.
- Multi choice используется только там, где исходная форма разрешает несколько вариантов.
- У каждого поля есть постоянный label; helper и error не заменяются placeholder.
- Необязательное поле комментария после вопроса всегда остаётся видимым, включая ответ `Нет`.
- Условно скрываются только вопросы, реально зависящие от пола; скрытый required-вопрос не блокирует отправку.
- Статус autosave имеет текстовые состояния `Сохраняем…`, `Сохранено`, `Не удалось сохранить — повторить`.
- Состояние, выбор и ошибка не передаются одним цветом.
- Все группы используют semantic `fieldset/legend`; клавиатурный focus заметен.
- Движение уважает `prefers-reduced-motion`.
- Интерфейс не ставит диагнозов и не обещает экстренную помощь.

Новый визуальный макет на этом этапе не требуется: утверждённый completion screen меняет только действия и текст состояния. Super Design применяется, если реализация обнаружит действительно новый экран, а не для повторного рисования уже согласованной системы.

### Requiredness V1

- Вопросы 1–43 и 45 обязательны, когда видимы.

### Формат шаблона

Шаблон хранится как версионируемый JSON-файл в кодовой базе, а не как редактируемые строки в БД. Минимальная структура:

```json
{
  "version": "health-profile-v1",
  "title": "Профиль здоровья",
  "sections": [
    {
      "key": "personal",
      "title": "Личные данные",
      "questions": [
        {
          "key": "full_name",
          "type": "text",
          "label": "Ваше имя, фамилия",
          "required": true
        }
      ]
    }
  ]
}
```

Разрешённые типы V1: `text`, `textarea`, `number`, `date_or_age`, `single_choice`, `multi_choice`, `scale`. Документы остаются отдельным модулем. На старте приложения и в тестах файл проходит schema validation, проверку уникальности `section.key`/`question.key` и точного общего количества.

После первой production-отправки версия шаблона неизменяема. Любое смысловое изменение создаёт новую версию; submission всегда хранит использованную версию.

## 9. Технологический стек

### Web-приложение

- Python + FastAPI.
- Jinja2 для серверного HTML.
- Vanilla JavaScript для autosave, состояний загрузки и небольших динамических раскрытий.
- Обычный CSS по утверждённым токенам; без SPA-фреймворка и обязательного frontend build pipeline.
- Шрифты Manrope и Cormorant Garamond self-hosted, чтобы внешний font CDN не видел посещение анкеты.

### Данные

- PostgreSQL как единственная рабочая БД.
- SQLAlchemy 2 для явных транзакций и моделей.
- psycopg 3 как драйвер.
- Alembic для последовательных миграций.
- UUID primary keys и `TIMESTAMPTZ` для временных значений.

### Файлы и внешняя инфраструктура

- Private S3-compatible object storage.
- Presigned PUT/GET URL с коротким сроком действия.
- ClamAV для malware scan.
- Один production email provider; медицинские ответы в письма не включаются.

### Проверка

- pytest для доменной логики, маршрутов, БД и security regression.
- Браузерные тесты ключевого пути и responsive-проверка.
- Линтер/форматтер и dependency lock выбираются в плане реализации без добавления второго frontend-стека.

## 10. Архитектура приложения

```text
Browser
  │ HTTPS, Jinja HTML, small JSON/form requests
  ▼
FastAPI modular monolith
  ├─ access: public entry, consent, magic link, OTP, sessions
  ├─ questionnaire: template, answers, progress, review
  ├─ submissions: validation, immutable snapshots, latest version
  ├─ documents: upload intents, status, authorized download/delete
  └─ audit: append-only security and data-access events
        │                    │
        ▼                    ▼
   PostgreSQL          Private S3 storage
        ▲                    │
        └──── scan worker + ClamAV
```

Это один deployable codebase. Web и scan-worker запускают разные команды из одного образа. Отдельный broker не используется: долговечное состояние проверки уже находится в `documents` PostgreSQL.

### Правила модулей

- HTTP-слой проверяет вход, session, CSRF и переводит ошибки в пользовательские состояния.
- Доменная операция владеет транзакцией submit/login/edit, а не цепочка обработчиков.
- Шаблон анкеты читается как immutable application data.
- ORM-модели не передаются напрямую в Jinja или будущий внешний контракт; представление получает минимальный view model.
- Интеграционный код не создаётся до появления реальной платформы и её контракта.

## 11. Модель данных

Все чувствительные таблицы имеют `workspace_id`, `created_at` и необходимые индексы. Имена полей ниже фиксируют смысл, а физическая миграция уточняет типы и индексы без изменения модели.

### `workspaces`

- `id`, `name`, `public_slug`, `status`.
- `public_slug` уникален, непрогнозируем и может быть ротирован, но не считается credential.

### `clients`

- `id`, `workspace_id`, `email_normalized`, `email_display`, `status`, `last_access_at`.
- Unique `(workspace_id, email_normalized)`.
- Нормализация ограничивается trim + case-fold домена/адреса; сервис не делает опасных provider-specific преобразований вроде удаления точек.

### `consents`

- `id`, `workspace_id`, `client_id`, `policy_version`, `text_hash`, `accepted_at`.
- Append-only. Изменение политики требует нового согласия перед дальнейшим вводом или загрузкой.

### `login_challenges`

- `id`, `workspace_id`, `email_normalized`, `magic_token_hash`, `code_hash`, `expires_at`, `attempt_count`, `resend_after`, `consumed_at`, `invalidated_at`, `ip_fingerprint`.
- Хранит также `policy_version`, `consent_text_hash`, `consent_accepted_at` до успешной привязки к client.
- Сырые token, code и IP не сохраняются.

### `sessions`

- `id`, `workspace_id`, `client_id`, `session_token_hash`, `idle_expires_at`, `absolute_expires_at`, `revoked_at`, `last_seen_at`.
- Idle expiry — 14 дней, absolute expiry — 30 дней. Повторный вход восстанавливает серверный draft.

### `questionnaire_responses`

- `id`, `workspace_id`, `client_id`, `questionnaire_version`, `status`, `current_revision`, `last_submitted_version`, `current_section_key`, `updated_at`.
- В V1 один response на `(workspace_id, client_id, questionnaire_version)`.
- `status`: `draft`, `submitted`, `editing`.

### `answers`

- `id`, `workspace_id`, `response_id`, `question_key`, `value_jsonb`, `revision`, `updated_at`.
- Unique `(response_id, question_key)`.
- `value_jsonb` валидируется по типу вопроса; комментарий является частью значения и не исчезает при смене radio.

### `submissions`

- `id`, `workspace_id`, `response_id`, `version`, `questionnaire_version`, `answers_snapshot_jsonb`, `content_hash`, `idempotency_key`, `submitted_at`.
- Unique `(response_id, version)` и `(response_id, idempotency_key)`.
- Append-only; update/delete запрещены роли приложения, кроме отдельной юридически контролируемой процедуры удаления клиента.

### `documents`

- `id`, `workspace_id`, `client_id`, optional `response_id`, optional `question_key`.
- `object_key`, `original_name`, `declared_mime`, `detected_mime`, `size_bytes`, `sha256`.
- `status`, `scan_attempts`, `next_scan_at`, `scan_lease_until`, `rejection_reason`, `uploaded_at`, `ready_at`, `deleted_at`.
- `status`: `uploading`, `quarantined`, `scanning`, `ready`, `rejected`, `deleted`.

### `audit_events`

- `id`, `workspace_id`, optional `client_id`, `actor_type`, `event_type`, `target_type`, `target_id`, `occurred_at`, `request_id`, `metadata_jsonb`.
- Append-only; metadata не содержит ответов, email, token, code или имён файлов.

## 12. Состояния и транзакции

### Autosave

- `radio/select`: отправка сразу после изменения.
- `text/textarea`: debounce около 700 ms и обязательная отправка на `blur`.
- `Продолжить` ждёт активный save request; при ошибке не делает вид, что данные сохранены.
- Клиент отправляет `expected_revision`. Несовпадение возвращает `409 Conflict`, после чего UI загружает серверную версию и явно предлагает повторить изменение.
- Медицинские ответы не сохраняются в `localStorage`, `sessionStorage`, URL или analytics.
- Без JavaScript секция сохраняется обычным POST при переходе дальше; JS только улучшает обратную связь и частоту сохранения.

### Final submit

Одна транзакция:

1. Блокирует response.
2. Проверяет только видимые required-вопросы по зафиксированной версии шаблона.
3. Нормализует и сериализует полный snapshot.
4. Создаёт submission с idempotency key и следующим version.
5. Обновляет response в `submitted` и `last_submitted_version`.
6. Добавляет audit event.

При повторе того же запроса возвращается уже созданный submission. Частичный snapshot невозможен.

### Edit

Переход `submitted → editing` выполняется транзакционно. Answers доступны для изменения только в `draft/editing`; в `submitted` они read-only. Отмена или истечение сессии не меняет последнюю отправку.

## 13. Passwordless security

- Magic token — криптографически случайный, одноразовый, срок действия 15 минут; в БД хранится его SHA-256 hash.
- OTP — шесть цифр, тот же challenge, максимум пять неверных попыток; из-за малого пространства кодов в БД хранится keyed HMAC с отдельным server secret, а не обычный быстрый hash.
- Resend доступен через 60 секунд и инвалидирует старый challenge.
- Ответы email-формы нейтральны против enumeration.
- Rate limit считается по workspace + HMAC-нормализованного email + HMAC-IP на основании недавних challenge; raw IP не хранится.
- Email URL несёт token только в fragment: fragment не отправляется в HTTP request и Referer. Минимальная страница без сторонних ресурсов применяет `Referrer-Policy: no-referrer`, same-origin JS делает POST exchange и немедленно очищает history. Обычный GET, включая email-link scanner, challenge не потребляет; если JS недоступен, клиент использует код из того же письма.
- Session token хранится в БД только как hash.
- Cookie: `Secure`, `HttpOnly`, `SameSite=Lax`, узкий `Path`; session id ротируется после входа.
- Все state-changing запросы защищены CSRF-токеном и проверкой Origin.
- Строгие CSP, `frame-ancestors`, HSTS и `X-Content-Type-Options` задаются централизованно; Jinja autoescape обязателен для ответов и имён файлов.
- Ошибки, access logs и request-body logging никогда не содержат magic token, OTP или session token.
- Turnstile не включается заранее. Он добавляется на email/resend только после подтверждённого abuse, чтобы не усложнять нормальный путь клиента.

## 14. Документы

### Ограничения V1

- Разрешены PDF, JPEG, PNG, HEIC.
- Максимум 25 MB на файл.
- Максимум 10 файлов в одной партии выбора.
- Документы необязательны и принадлежат client card; их можно добавить после отправки.
- Незавершённая или отклонённая загрузка не повреждает ответы и не блокирует submit анкеты.

### Поток загрузки

1. Авторизованный клиент запрашивает upload intent с именем, размером и MIME.
2. Сервер проверяет allowlist/лимиты, создаёт `documents: uploading` и выдаёт короткий presigned PUT на сгенерированный `quarantine/{uuid}` key.
3. Клиент загружает объект напрямую в private storage и подтверждает завершение.
4. Сервер проверяет существование/размер объекта и переводит запись в `quarantined`.
5. Worker берёт запись через `FOR UPDATE SKIP LOCKED` и ограниченный lease, потоково определяет magic bytes, считает SHA-256 и запускает ClamAV; временная ошибка назначает `next_scan_at` с ограниченным backoff.
6. Успех даёт `ready`; несоответствие, вредоносный файл или исчерпанные повторы дают `rejected` с безопасным сообщением.
7. Скачать можно только `ready`-файл по короткому presigned GET после повторной проверки client/workspace и audit event.

Клиентское расширение и `Content-Type` не считаются доказательством формата. Имена объектов генерирует сервер. Bucket закрыт, listing запрещён, шифрование at rest включено. Rejected/quarantine objects удаляются по короткой операционной политике; готовые — по утверждённому сроку хранения или запросу удаления.

## 15. Multi-tenant изоляция

- Каждый запрос сначала разрешает workspace из публичного slug или session.
- Перед запросами к чувствительным таблицам транзакция задаёт локальный tenant context.
- PostgreSQL RLS включён и принудителен (`FORCE ROW LEVEL SECURITY`).
- Роль приложения не владелец таблиц и не имеет `BYPASSRLS`/superuser.
- Foreign keys и unique constraints не позволяют связать сущности разных workspace.
- Автоматические тесты пытаются читать, менять, отправлять и скачивать данные соседнего workspace и ожидают отказ/пустой результат.

Проверки приложения остаются обязательными; RLS — второй барьер, а не замена авторизации.

## 16. Маршруты V1

### HTML

- `GET /i/{public_slug}` — начало/согласие.
- `POST /i/{public_slug}/consent` — принять согласие.
- `GET|POST /i/{public_slug}/access` — email и нейтральный результат отправки.
- `GET /auth/magic` — минимальная landing page; token остаётся только в URL fragment и не потребляется GET-запросом.
- `POST /auth/magic` — одноразово обменять fragment token на session и очистить URL redirect-ом.
- `POST /auth/code` — проверить OTP.
- `POST /auth/logout` — отозвать session.
- `GET /q/{section_key}` — раздел анкеты.
- `POST /q/{section_key}` — non-JS сохранение раздела/переход.
- `GET /review` — проверка.
- `POST /submit` — идемпотентная отправка.
- `GET /complete` — завершение и текущая версия.
- `POST /edit` — начать исправление.

### Малые JSON endpoints

- `PUT /answers/{question_key}` — autosave одного ответа с revision.
- `POST /documents/uploads` — создать upload intent.
- `POST /documents/{id}/complete` — завершить прямую загрузку.
- `GET /documents/{id}/status` — получить статус.
- `POST /documents/{id}/download` — получить короткую download URL.
- `DELETE /documents/{id}` — удалить собственный документ с audit.

Endpoint не принимает `workspace_id`, `client_id` или `response_id` как доверенные полномочия от браузера; scope выводится из session.

## 17. Ошибки и восстановление

| Ситуация | Поведение |
|---|---|
| Неизвестный/отключённый public slug | Нейтральная 404-страница без раскрытия workspace |
| Не отмечено согласие | Inline error, focus на checkbox, продолжение заблокировано |
| Письмо задержалось | Экран показывает code input, resend countdown и смену email |
| Link/code истёк | Сохраняется email, предлагается новая отправка |
| Пять неверных кодов | Challenge закрыт; новый после rate-limit |
| Autosave offline/5xx | Ответ остаётся в активном поле, статус ошибки и явный retry; переход дальше заблокирован при unsaved change |
| Revision conflict | `409`, показать, что ответ изменён в другой вкладке, загрузить серверное значение |
| Submit повторён | Вернуть тот же submission по idempotency key |
| Upload оборвался | `uploading` истекает, объект/запись очищаются; ответы не затрагиваются |
| Scan worker перезапущен | Истёкший lease позволяет безопасный повтор |
| Файл отклонён | Безопасная причина и возможность удалить/загрузить другой |
| БД недоступна | Не подтверждать save/submit; healthcheck fail, без локального «успеха» |

## 18. Privacy, аудит и удаление

- Согласие хранится с версией и hash точного текста.
- Production запуск запрещён без юридически утверждённых текста, политики, срока хранения и контакта для запроса удаления.
- Обычные логи содержат request id, route template, status, latency и технический error code, но не body, query token, email, ответы или имена файлов.
- Audit фиксирует вход, отзыв session, submit, начало edit, upload/ready/rejected/download/delete и административный экспорт/удаление, когда они появятся.
- Запрос удаления обрабатывается отдельной операторской командой без создания кабинета: отзывает sessions, удаляет объекты, затем данные клиента в одной контролируемой процедуре и оставляет минимальную безличную запись факта выполнения, если это разрешено политикой.
- Внешние OCR/AI-провайдеры в V1 не получают данные.

Эта спецификация задаёт технические меры, но не заменяет юридическое заключение о персональных данных и данных о здоровье.

## 19. Наблюдаемость и эксплуатация

### Процессы

- HTTPS reverse proxy/platform ingress.
- FastAPI web process.
- Scan worker из того же codebase.
- PostgreSQL.
- Private S3-compatible storage.
- ClamAV service/sidecar.
- Email provider.

### Сигналы

- Доля успешной отправки access email, consume magic link и OTP failures без адресов.
- Autosave latency/error rate и submit latency/error rate.
- Количество документов по техническим status, возраст старейшего `quarantined`, scan failures.
- DB pool saturation, migration status, storage/ClamAV availability.
- Alerts не содержат медицинские ответы.

### Надёжность

- Alembic migration запускается отдельным release step перед новой версией приложения.
- PostgreSQL backup выполняется регулярно; object storage versioning/lifecycle определяется production policy.
- Restore drill проверяет согласованное восстановление DB и объектов, а не только наличие backup.
- Deploy обратимо переключением версии приложения; необратимые destructive migrations не входят в один release с удалением старого кода.

## 20. Будущая интеграция

Основной путь — top-level redirect/link. До появления конкретной платформы connector, webhook table и универсальный API не создаются.

Когда контракт появится:

1. Платформа передаёт подписанный короткоживущий handoff с workspace и return URL, но не с медицинскими данными.
2. Клиент всё равно подтверждает email, если между системами нет отдельно утверждённого identity trust.
3. После submit модуль отправляет минимальный HMAC-подписанный event с submission id/version; получатель забирает данные по авторизованному server-to-server запросу.
4. Повторы идемпотентны, delivery status аудируется.

Iframe рассматривается только как отдельный проект после проверки cookie, CSP, мобильного поведения и модели доверия доменов.

## 21. Проверки и acceptance criteria

### Контент и UX

- [ ] JSON-шаблон посимвольно совпадает с Drive-контрактом 46 вопросов по label, helper, options и order; required/condition совпадают с политикой раздела 8.
- [ ] Сумма вопросов по разделам равна 46; ключи уникальны; template version неизменяема после первой отправки.

- [ ] В каждой single-choice группе невозможно выбрать два варианта.
- [ ] Комментарий остаётся видимым при каждом radio-варианте, включая `Нет`.
- [ ] Keyboard-only путь проходит consent, email, code, все типы вопросов, review, submit и документы.

### Доступ

- [ ] Public link без email verification не раскрывает client existence или данные.
- [ ] Magic link и OTP одного challenge взаимно инвалидируются после первого успеха.
- [ ] Expiry, resend cooldown, пять попыток и rate limits проверены автоматическими тестами.

- [ ] Autosave восстанавливается после logout/login и не использует browser storage для ответов.
- [ ] Две вкладки дают детерминированный `409`, а не last-write-wins.
- [ ] Double submit создаёт ровно один submission для одного idempotency key.
- [ ] После начала edit читающая сторона продолжает видеть предыдущий submission.

- [ ] Перезапуск worker после lease возвращает карантинный файл в обработку без дублирования.
- [ ] Ошибка/отмена upload не меняет answers и не блокирует submit.

- [ ] Логи и error reporting проходят проверку на отсутствие email, answer body, filename и tokens.

## 22. Bulletproof Challenge Loop — итог

### 22.1 Проверка проблемы

Каждый исходный запрос имеет прямой механизм: одна ссылка — public workspace slug; неизвестный email — self-entry; лёгкий вход — magic link + code fallback; длинная форма — server autosave; исправления — draft + immutable submissions; анализы — private storage + scan; будущая платформа — top-level boundary.

### 22.2 Альтернативы

- SQLite/локальные файлы проигрывают подтверждённому production-внедрению и создают обязательную миграцию.
- SPA/микросервисы/queue stack увеличивают количество отказов и не сокращают путь клиента.
- Секретная client-link упрощает один экран, но переносит безопасность на пересылаемый URL.

Выбранный модульный монолит остаётся самым маленьким решением, которое выдерживает требования к данным здоровья.

### 22.3 Code-for-code

- Нативные HTML radio/fieldset вместо собственного selection-компонента.
- Server-rendered sections вместо SPA-router/state store.
- PostgreSQL unique constraints/RLS вместо дублирующих самописных механизмов.
- `documents` status + lease вместо Redis/Celery.
- Один versioned JSON template вместо builder/schema UI.
- Один mutable answer set + immutable submission snapshots вместо event sourcing.

### 22.4 Остаточные риски

| Риск | Статус |
|---|---|
| Source sheet не содержит required-флагов | Явная политика раздела 8 входит в утверждение владельцем и автоматические schema tests |
| Юридический текст и retention зависят от страны/оператора | Production gate, техническое версионирование предусмотрено |
| Один email на человека не покрывает семейные профили | Осознанное ограничение V1; расширять только по реальным кейсам |
| PostgreSQL как очередь scan-worker имеет предел throughput | Достаточно V1; broker добавляется только по метрикам |
| Будущая платформа неизвестна | Connector намеренно не строится без контракта |

## 23. Оркестрация разработки: Sol Max → Luna Max

### Модели и полномочия

- Главная задача работает на `gpt-5.6-sol` с reasoning `max`. Sol — единственный оркестратор и финальный приёмщик.
- Исполнители запускаются на `gpt-5.6-luna` с reasoning `max`. Одна Luna получает одну атомарную задачу и не меняет scope самостоятельно.
- Luna не принимает собственную реализацию как независимое review и не делегирует другим Luna.
- На обычной фазе одновременно работают не более трёх Luna и только с непересекающимися write sets. Общая миграция, один контракт или одна таблица не делятся между параллельными агентами.
- Каждая задача изменения ограничена максимум тремя файлами; более крупная фаза сначала дробится Sol.
- Sol не пишет feature-код вместо Luna. Он читает diff/артефакты, повторяет критические gates, сопоставляет результат с acceptance criteria и либо принимает, либо возвращает конкретный `finding_id`.

Перед первой фазой фактические model/reasoning фиксируются в handoff. Если текущая главная задача не запущена на Sol Max, реализация не начинается до переключения модели или новой явно созданной задачи.

### Контракт результата Luna

```text
status: PASS | RETURN | BLOCKED
artifact: path или scoped diff
scope: что прочитано, изменено и сознательно не тронуто
gates: команда/проверка → результат → evidence
findings: id, severity, file:line, proof, minimal fix, verification
open_decisions: только развилки, требующие владельца
proof: static | test | runtime | external approval
```

`UNKNOWN` не считается `PASS`; статическая проверка не выдаётся за runtime evidence.

### 12 стадий Bulletproof

| Стадия | Luna-роли | Gate Sol |
|---|---|---|
| 1. Research | `Research`, при реальном втором разрезе `Security/Product Research` | Каждый вывод имеет источник; неизвестное обозначено; кода и записей во внешние системы нет |
| 2. Spec | `Spec`, `Content/UX` | Scope и каждый acceptance criterion проверяемы; 46 вопросов сверены с Drive-контрактом; владелец утверждает продукт |
| 3. Plan | `Planner` + независимый `Challenger` | Challenge Loop покрывает каждый criterion, сравнивает альтернативы и удаляет code-for-code; задачи ≤3 файлов |
| 4. Implement | отдельный `Builder` на атомарный write set | TDD red→green, scoped diff и применимые compile/lint/test gates |
| 5. Self-Audit | тот же `Builder` | Карта criterion → code/test; unrelated changes отсутствуют; это ещё не независимый review |
| 6. Verification | независимый `QA` | Полные применимые tests; blocking finding воспроизводим; false positives отброшены |
| 7. Impact | `QA` отдельным проходом | Consumers, contracts, migrations, concurrency, zero/large input, rollback и совместимость проверены |
| 8. Integration | `Integration`, при UI-изменении `Content/UX` | E2E проходит public link → email → анкета → submit → document ready/download |
| 9. Code Review | свежий reviewer по `code-reviewer.md` | Findings имеют file:line, proof и minimal fix; high/critical и доказанные release-blocking medium закрыты |
| 10. Security | `Security/Privacy` | Auth, CSRF, sessions, RLS, tenant isolation, logs, uploads, ClamAV, secrets и dependency scan прошли |
| 11. Fix/Recheck | `Builder` по конкретным finding IDs, затем targeted `QA/Security` | Повторены упавшие gates и impact; крупная правка снова проходит review/security |
| 12. Release | `Release/Ops` | Migration/rollback, backup restore и production smoke доказаны; deploy только по явному разрешению пользователя |

### Review stack

1. На каждой фазе: Builder self-audit → независимый Luna QA → Sol acceptance.
2. На security-sensitive фазах: дополнительно Luna Security/Privacy.
3. Перед release: свежий `code-reviewer` на сильной reasoning-модели; затем `review-minimax.md` и `review-qwen.md` через OpenCode, только если реальные provider/config доступны.
4. Если OpenCode недоступен, запускаются два свежих Luna Max по тем же профилям, но результат явно помечается как same-family fallback, а не cross-model review.
5. Reviewer не исправляет код. Sol возвращает доказанный finding Builder’у и принимает только повторно проверенный fix.

Постоянный «совет агентов» не создаётся. Для обычной атомарной фазы достаточно Builder + QA; дополнительные роли включаются по риску, а не автоматически.

### Человеческие gates

- Владелец продукта утверждает spec, requiredness и implementation plan.
- Юридически ответственный утверждает consent, privacy policy, retention и deletion.
- Пользователь отдельно разрешает production deployment и любые платные/provider действия.

## 24. Граница следующего шага

После утверждения этой спецификации Sol Max запускает Luna Planner + Luna Challenger и создаёт отдельный пошаговый implementation plan с небольшими проверяемыми этапами. До утверждения плана прикладной код, инфраструктура и зависимости не создаются.
